# V6.1 Phase 4：戰鬥效能診斷與優化

基準版本 `e40a2e3`（Phase 3）；工作分支 `feature/v6.1-performance`。本階段不改題目、答案正規化、分數題格式、傷害、怪物數值、EXP 曲線、UI 版型、信箱、老師發放或家具功能。沒有操作正式 Sheets。

## 原因與歷史定位

- `9b5ff3d` 的 V6 Phase 3 全画面對戰讓 `renderBattleQuestion()` 直接呼叫 `renderBattle()`。選技能及答題後會重新建立舞台與整個操作區，大圖與技能按鈕也一起重建。這放大舊有重 render 的成本。
- `1278421` 的 V6 答題冪等是必要的正確性保護，但每批原本查兩次交易索引並全讀學生寵物與挑戰紀錄；獎勵紀錄增長時，鎖內工作量隨之增加。
- V6 Phase 1 加入永久技能強化，登入／升級 bundle 的技能快取未命中時，原本全讀強化紀錄。不是每次攻擊查強化 Sheet。
- Phase 1～3 的批量石頭、老師批次、stone sprite、家具 Lazy Loading 沒有出現在每題 API 路徑。正常戰鬥不讀學生道具，不抓 upgrade bundle，也不載入家具。
- 620ms 攻擊動畫在 `5e1dff3` 的 V5.10.6 已存在，不是這次改版新加的等待；本階段不縮短動畫。

## 流程逐段診斷

下表的 API 次數是正常成功路徑；一個 POST 對應一次 doPost 執行。瀏覽器測試使用模擬 API，並未量到正式 Apps Script 執行時間。讀取次數指 getValues/getDisplayValues/getValue 或 Values.batchGet，不計 metadata 方法及已命中的 header cache。

|步驟|API／Apps Script 次數|Sheet 與 cache|DOM／圖片|
|---|---|---|---|
|冷進入科目|最多5／5|單科題庫、怪物、背景、寵物戰鬥設定、存檔；前4项 cache miss各1次全表讀，存檔1次全表讀。0寫入|選擇／首次戰鬥建立DOM；圖片首次載入|
|同科已載入再進入|通常1／1|只查存檔；若有未同步批次會先重送|新戰鬥建立一次DOM|
|選技能、顯示題目|0／0|技能與bonus在 session 記憶體；题庫在記憶體|以前重建舞台＋操作區；現在只更新題目區與選取狀態|
|作答、判定|0／0|前端 normAns 與 EXP 規則不變；pending 累積|停用現有按鈕；不重新抓 student state|
|動畫、扣HP|0／0|傷害來自 session 技能；不查石頭／庫存／強化表|保留sprite節點，更新HP、結果、動畫與怪物名稱；同來源不再設定src|
|正常下一題|0／0|本機題庫補題，沒有後端取題|只建立下一題內容，保留舞台與技能按鈕|
|滿12題同步|1／1|伺服器重新判定答案，讀永久 batchId 收據與該學生必要列；準備1次、原子提交1次寫入|背景同步，無全畫面重建、無 student/config refresh|
|第3次錯誤|1／1，若有舊批次另計|維持立即本機鎖定與強制同步；後端也在3錯停止處理|只切換結束操作區；舞台不重建|
|儲存並離開|待同步各批1次＋存檔1次|沿用原 save API、payload 與先同步後存檔順序|清理舞台、timer、動畫待完成項|
|切回小屋／升級／家具|待同步背景提交|新增離頁同步；timeout 原 batchId 留在既有 localStorage。登出前也先持久保存 pending|清理 DOM、timer、session，不讓晚回應重建舞台|

技能強化取得發生於登入已有的 core bundle，不額外增加戰鬥 API。初始化必要讀取改成並行，沒有新增 bundle／action。已成功載入的空設定清單也會記住，不反覆請求；失敗仍能重試。

新批次第一次會保留 SUBMITTED，再以一次原子 batchUpdate 更新分數、EXP 與 COMMITTED 收據；兩次寫入沒有為了效能合併或移除。重送仍回第一次結果，未知交易仍停止重發。持有原 ScriptLock 下讀取可變資料，不快取分數或交易判斷。準備後只確認保留列的 batchId，不再重掃整本獎勵歷史。

獎勵的學號／batchId／狀態三欄仍掃一次，以確保永久去重及未知交易防護；不是O(1)，但已減少重複掃描。不新增索引表或依賴可過期的快取作安全判定。學生資料只讀學號索引與匹配列；散落列用 Values.batchGet 批讀，每80個range分段，避免長歷史產生過大URL。既有環境已啟用的 Google Sheets API 足夠，沒有新服務。

初次讀共用設定／題庫在 cache miss 時仍有 getDataRange，題目顯示值來源不變；同步若題目快取剛過期，也可能有一次共用題庫讀取。V5.10.5存檔讀寫核心本階段不修改，因此存檔查詢仍有全表讀取，存檔寫入仍有既有逐欄寫入；這些不是每題路徑。資料量增加後可另量測，不在本階段改存檔交易格式。

## Chrome時序與DOM對照

`tests/v610-battle-performance-ui.test.cjs` 在桌面1440×1000、平板768×1024、手機390×844，對相同 fixture 執行舊版與新版。每支模擬 API 固定100ms，不代表正式網路或實體手機速度；毫秒值隨機器負載有變動，測試以結構與次數斷言為主。

|量測|修改前|修改後|
|---|---|---|
|冷進入科目|314～324ms|104～106ms|
|第一題出現（含進入）|332～342ms|116～120ms|
|首次點技能→題目|3.3～4.0ms|0.3～0.5ms|
|後續點技能→題目|1.2～2.3ms|0～0.3ms|
|答對→動畫class開始|0.3～1.1ms|0.1～0.9ms|
|答對→下一題可操作|623～638ms|622～636ms|

動畫完成沒有顯著時間縮短，因為保留原620ms節奏；差異在消除重建與縮短冷初始化的串行等待。動畫先啟動，再做12題批次的storage準備；玩家動畫重啟以 animationName 確認樣式代替 offsetWidth 同步幾何量測。瀏覽器測試也確認 CSS Animation 實際處於 running，不只檢查class名稱。

5次作答（含普通、屬性、Lv30專屬、有／無加成）與第12題門檻的fixture對照：

- 每題正常API：前後皆0；達12題共1次sync，battle config fetch與enhancement API皆0。
- 戰鬥舞台full render：10→0；操作區full render：10→0。首次進場、鎖定轉場可建立必要區塊，不是每題重新render。
- 新建戰鬥圖片節點：20→0；同寵物／怪物的src重設0。連續擊敗3隻怪物，玩家與技能按鈕仍是同一節點。
- 技能陣列重算：15→0（進場只算一次）。切出戰鬥後session清除，再進／續戰重新建立。
- 該fixture批次storage呼叫前後皆8；舊版同步storage耗時約0.1～0.7ms、新版約0.1ms，未發現主線程瓶頸，因此保留原永久重試保存方式。題庫JSON只在首次載入保存，不每題序列化。
- 本機HTTP真實瀏覽器cache：寵物／怪物／背景前後都是各下載1次。改善的是舊版重新建立與解碼圖片的機會，沒有宣稱舊版每次都重傳網路圖片。

攻擊timer由原Set管理，完成即移除，切頁會清除並完成未結束動畫Promise。不增加animation listener、全域事件或其他動畫timer。

## 素材稽核

本階段沒有改任何畫質素材。`BATTLE001.png` 為1590×989、2,422,633 bytes；`PET004_3.png`為1254×1254、2,102,349 bytes；`PET006_3.png`為1254×1254、2,087,645 bytes。這些素材比畫面實際顯示尺寸大，首次下載／解碼仍可能影響較慢裝置。後續可另做適合顯示尺寸的WebP／縮圖評估，本次保留原素材與畫質。
