# V6.0 第二階段：整點寵物信箱屬性石

僅變更整點禮物與信箱領取流程，不修改對戰 UI。沿用第一階段的 12 種 STONE_* 道具 ID 與學生道具庫存。

## 掉落規則

apps-script/Code.gs 的 HOURLY_STONE_DROP_RATE_V600 = 0.50（範圍 0～1）控制每封整點禮物抽中石頭的機率。設為 0 可停用新石頭掉落，不影響既有信件。

hourlyPetGiftV600_() 從寄信寵物的寵物戰鬥設定讀取屬性；沒有該設定時讀取寵物設定的屬性。屬性未知或道具設定不存在時保留舊禮物流程。共用設定使用既有快取。

抽中石頭後：1 顆 80%、2 顆 10%、3 顆 6%、4 顆 3%、5 顆 1%。未抽中時呼叫原封不動的 randomGift_()，保留糖果與寶物原機率。石頭信件標題使用 XX之石，內容顯示數量及技能強化用途。

## 領取與併發

單封 claimMail / claimMailFast 與全部 claimAllMailFast 共用 ScriptLock 與 claimMailLockedV600_，沿用既有 API 參數及回傳格式。

信箱新增一欄「領取交易」，儲存 JSON：itemId、quantity、row、before、after。這只是入帳恢復紀錄，不是另一套庫存。永久道具數量仍只在「學生道具」。

流程：驗證信件學號與附件 → 記錄目標道具列及加總前後數量並 flush → 只寫目標數量並 flush → 標記該信件已領取。已領取重試不入帳；未領取但有紀錄的重試，以目前數量判斷是否已入帳。數量或列身分不符時停止，請老師確認，避免猜測而重複發放。

信箱入帳、老師發屬性石、使用屬性石共用同一把鎖。未完成信件交易會擋住同道具的其他領取、發石頭、使用；未完成技能強化會擋住石頭領取。全部領取先恢復未完成信件，每封獨立記錄；中途失敗可再次收取。批量領取共用一次道具與強化紀錄讀取，不整張寫回。老師批量發其他道具也改成只更新受影響數量，避免覆蓋同時入帳的石頭。

前端領取期間停用單封、全部及更新按鈕，單封與全部共享 busy 防連點；以後端回傳更新庫存快取。逾時讀取實際信箱，後續用原信件 ID 重試。

整點產信同樣加鎖，信件 ID 由學號與整點時間組成；發信已成功而更新最後整點失敗時，再次執行會跳過既有 ID。

Google Sheets 跨列寫入沒有資料庫交易保證；本版使用持久紀錄與共用鎖恢復。不要在交易未完成時手動改動相關信件或道具列。既有登入與舊 API 驗證政策未在此階段重構。

## 部署與資料結構

1. 將此版 Code.gs 放入原 Apps Script 專案。
2. **再次執行 setupOrUpgradeV600()**，補上「信箱」末端的「領取交易」欄；舊欄位、舊信件、學生資料均保留。重跑不重複新增石頭，不發放或重設道具。
3. 更新原 Web App 部署版本，保持原 exec URL；發布 app.js。

新增 API：無。新增工作表：無。新增欄位：信箱／領取交易。

## 驗證

在專案根目錄執行：

~~~powershell
node --check app.js
Get-Content -Raw -Encoding UTF8 apps-script/Code.gs | node --check
node tests/v600-mail.test.cjs
~~~

信箱測試同時跑第一階段回歸。涵蓋所有 12 種屬性、精確機率邊界與分桶、原禮物回退、整點發信去重、單封／全部交錯、加鎖、局部寫入、入帳前後故障恢復、強化／領取互斥、新庫存列、既有糖果及前端連點與快取更新。環境為記憶體 Sheets 與模擬 DOM，不連線或修改正式 Sheet；正式部署後仍需用測試學生驗證發信與領取。

## 回復第一階段

回復前先用本版完成所有「是否領取」未完成且有「領取交易」的信件，確認已入帳並標記已領取，再發布第一階段 Commit（4a45261）的 app.js 與 Apps Script 版本。未完成交易不應直接交給舊版處理，否則舊版不認識恢復紀錄，可能重複入帳。

保留新增欄位、既有石頭信件與全部學生道具數量，不刪除、不重設。已完整領取的石頭仍可於第一階段強化系統使用；舊版領取路徑的併發風險也會恢復，因此建議優先設掉落常數為 0 並部署此版，以停用新掉落、保留安全領取。
